# 夙愿·AI Agent聪明度管理框架

**一句话结论：** AI Agent 帮你干活时"越用越蠢"，根因不在模型——是你没管好它的**上下文聪明区**、没对齐**信息**、没给对**工具**、没给对**方法论**。补上这四块拼图，Agent 能从"10分钟聪明、后面全是废话"变成"越跑越懂你"。

---

## 一、核心框架总览：聪明度管理四层模型

夙愿没明说但贯穿全程的心智模型：

| 层级 | 解决的问题 | 核心动作 |
|:--|:--|:--|
| **诊断层** | AI为什么变蠢？ | 识别四个根因 |
| **基础层** | 怎么让它不变蠢？ | 管上下文、给工具、给方法论 |
| **执行层** | 怎么让它干完活？ | 9步闭环工作流 |
| **进化层** | 怎么让它越用越聪明？ | 知识沉淀 + 最小必要干预 |

> 这四层不是并列的——**诊断层是入口，基础层是前提，执行层是路径，进化层是飞轮**。缺任何一层，Agent 都会在某个节点崩掉。

---

## 二、诊断层：AI变蠢的四个根因

### 1. 硬性根因：上下文超过「聪明区」

- **事实**：模型标称100万上下文，但真实有效注意力窗口只有约 **10万token**
- **表现**：超过10万→慢慢忘掉指令细节→重复犯错→漏关键信息→产出越来越烂
- **阈值**：10万开始警惕，15万必须收尾，**绝不让窗口超过30万**
- **工具**：装上下文进度条插件，实时盯住数字

> 金句：*不要让模型窗口超过30万，超过之后模型会变得很蠢很蠢。*

### 2. 软性根因：信息没对齐（乔哈里视窗）

- **本质**：你知道但AI不知道——它只能猜你的意图
- **后果**：猜测→走偏→返工→浪费上下文→进一步变蠢
- **解法**：用 Grade Skill 把脑子里的想法榨干，对齐后再干活

> 关键洞察：*AI不是你肚子里的蛔虫。信息没对齐就开工 = 注定返工。*

### 3. 能力根因：工具不到位

- **两种缺失**：
  - 能干但费劲：翻代码库没有LSP，翻15个文件读3000行才找到函数→上下文全浪费
  - 根本干不了：小红书反爬，不给API它永远搞不定
- **原则**：给对工具 = 省上下文 + 扩展能力边界

### 4. 路径根因：模型默认走平庸路线

- **本质**：AI是概率接龙——训练倾向于让它走"最快完成"的路径，不是"最好"的路径
- **表现**：代码能跑但结构垃圾、文案看似正确但毫无灵魂、打补丁式修改越改越烂
- **解法**：用方法论 Skill 把模型从默认路径推到非平庸路径

> 金句：*没有一个好的方法论来让它走更优质的路线，它就永远走平庸的路径。*

## 三、基础层：让AI变聪明的三根支柱

### 支柱一：管好上下文——时刻盯住聪明区

- **做法**：装进度条 → 实时盯 → 接近10万开始收束 → 15万前用 Handoff 交接
- **Handoff 机制**：写交接文档→开新会话→读取文档→继续干
- **Handoff 铁律**：
  - 已解决的不要写进交接（用 Compact 会混入无效信息）
  - 只写当前问题B的状态
  - 文件路径已有内容 → 只写路径，不复制粘贴
- **PRD 技巧**：聊完需求立刻写成PRD→新会话只读PRD→不再重复提问

> *下一个 Agent 永远无法访问本次对话——所以PRD必须逐项穷举每一个决策和边界条件，检验标准是：任何人/任何AI只读这份文档，零歧义、零追问。*

### 支柱二：给对工具——减少无效上下文消耗

- **LSP（语言服务协议）**：精准定位代码位置，从"翻15个文件读3000行"变成"一步到位"
- **Browser Use / Computer Use**：让Agent操作浏览器和桌面，写完代码自己跑测试
- **工具定义原则**：把"Agent自己摸索工具怎么用"的过程前置到Skill里，一次定义、多次复用

### 支柱三：给对方法论——改变模型默认输出路径

- **核心逻辑**：模型默认走的是"快速完成"路径→用精炼的方法论 Skill 把它推到"高质量"路径
- **Skill 设计原则**：少而精、方法论密度高、占用上下文极少（通常3-5句话）
- **效果**：同样的模型，有方法论 vs 没方法论，产出质量天差地别

> 金句：*方法论就是把模型从平庸路径推到非平庸路径的那只手。*

## 四、执行层：从想法到交付的9步闭环

### 流程图（夙愿的实际工作流）

```
Issue → Grade(对齐需求) → 原型(验证方案) → To PRD(沉淀文档) 
    → To Issue(垂直切片) → TDD(测试驱动写代码) 
    → 代码审查(核弹级) → E2E测试(端到端验证) 
    → 手工分组测试 → 完成 / Bug Fix(7阶段修复) → 循环
```

### 逐步拆解

**Step 0 · Issue：一切从Issue开始**
- Issue = 原始问题/需求/Bug反馈的总入口
- Grade聊完的需求写进Issue评论区
- PRD完成后也提交到Issue评论区
- Issue是整条链路的起点和终点

**Step 1 · Grade（榨干需求）**
- 核心 Skill：3句话，让模型像教练一样追问你
- 关键区别：**Grade的目标是"直到我们达成共识"，Plan模式的目标是"赶紧出计划"**
- 设计树方法论：逐一解决决策之间的依赖关系，每个分支走到底
- 行为规则：一次一个问题→等我回答→能查代码库就先查、别问我

> 用Plan模式聊需求 = 模型偷懒出计划；用Grade聊需求 = 模型把你的想法榨干。

**Step 2 · 原型（验证方案）**
- 场景：多个方案不知道哪个更好
- 做法：用原型Skill快速生成可测试的版本→跑一跑→数据说话

**Step 3 · To PRD（沉淀需求文档）**
- 为什么必须写：聊完需求时上下文往往已到15万，不能继续干活
- PRD包含：决策、约束、边界条件、被否决的方案
- 铁律提示词：*下一个Agent永远无法访问本次对话* → 逐项穷举，零歧义零追问

**Step 4 · To Issue（垂直切片拆分）**
- 按**垂直切片**拆分（每个切片独立完成：数据库→接口→页面），不是水平切片（先后端再前端）
- 好处：多个窗口并行、每个切片独立可验证、不需要互相等待
- 不确定则单窗口：贪快开太多窗口 → 断掉 → 搞混 → 得不偿失。**建议最多2-3个**

**Step 5 · TDD（测试驱动开发）**
- 流程：先写红灯测试→写最少代码让测试通过→重构
- 核心价值：代码有客观裁判（测试跑得过/跑不过）→逻辑上必须对
- 区别于文案：写代码有测试验证，写文案没有客观裁判→代码场景下TDD尤其有效

**Step 6 · 代码审查（核弹级别）**
- 来源：Cursor团队开源的review Skill，严格到"核弹级"
- 审查维度：
  - 结构简化（防打补丁式膨胀）
  - 一个文件不超过1000行（模型分批读=效果打折）
  - 去掉AI生成的垃圾代码模式
- 双重审查：Agent自审 + Codex自动PR Review（兜底）

**Step 7 · E2E测试（端到端验证）**
- 工具：Codex的Browser Use / Computer Use → 操作浏览器/桌面跑测试
- E2E Skill规则：
  - 先轻量验证（命令行查数据库），再重量验证（浏览器操作）
  - 遇到Bug：**只记录事实和复现步骤，不写修复建议**
  - 为什么不让它写建议：①上下文已很长 ②它的视角局限在单个Bug，可能忽略牵一发动全身的问题 ③模型给出的建议往往是打补丁

> *让E2E Agent写修复建议 = 邀请它给你的代码库打一堆补丁，最终整个代码库变成一堆补丁的缝合怪。*

**Step 8 · 手工分组测试**
- 分组逻辑：一条路径走完（注册→登录→充值→使用），不要来回切账号
- 发现问题：只记录→交给Bug Fix→不分析原因、不给建议
- 这是最后一道防线——模型不可靠，必须亲自测

**Step 9 · Bug Fix（7阶段修复）**
- 阶段设计（防打补丁式修复）：
  1. 读知识沉淀→看有没有踩过的坑
  2. 建立验证循环→代码级验证，不靠看
  3. 提出假设→建Debug探针→定位根因
  4. 修复→验证→整理代码结构
  5. 沉淀：业务术语→Context文档 / 陷阱→陷阱文档 / 架构决策→ADR文档
- 最多循环3轮→3轮搞不定说明方案层面有问题→停下来、重新审视

### 并行策略

- **To Issue后**：多个独立切片可以并行开窗口
- **建议上限**：2-3个窗口，多了容易搞混
- **防搞混**：不确定是否独立 → 单窗口

## 五、进化层：知识沉淀飞轮

### 为什么必须做知识沉淀

每个Agent会话都是**全新的**→VIP一天100次这个信息，上个会话说过，新会话不知道→Agent又问一遍→你觉得它蠢→其实是你没沉淀。

### 沉淀三类内容（以编程为例）

| 类型 | 内容 | 文档 |
|:--|:--|:--|
| 业务术语 | VIP=100次/天、SVIP=200次/天 | Context文档 |
| 已知陷阱 | 某个库的版本兼容问题、某个API的坑 | 陷阱文档 |
| 技术决策 | 为什么选A方案不选B | ADR文档 |

### 飞轮运转方式

```
每次开新会话 → 先读知识沉淀文档 → 干活 → 发现新东西 → 沉淀回去
                                                  ↑
                                        下次会话起点更高
```

- **效果**：节省几千行代码的翻阅→几十token一句话搞定
- **本质**：知识沉淀 = 把上下文从"每次重新探索"变成"持续积累复利"

## 六、底层原则

### 原则一：最小必要干预

- **含义**：给Agent目标，中间过程让它自己发挥——但关键路径上必须给到方法论
- **边界**：非必要不干预，但模型默认走平庸路径时，必须用最小干预把它推到正确路径
- **反面案例**：让AI改进Skill → 它会打补丁 → 过度干预 → 下次效果反而更差

> 金句：*你给AI改Skill，它就用打补丁的方式改——最后你的Skill变成了补丁的补丁的补丁。*

### 原则二：循环拉回机制

- **问题**：长对话中模型会漂移，忘了自己在干什么
- **解法**：在Skill里嵌入循环结构（While循环伪代码）→ 每完成一步回顾下一步 → 不漂移
- **Go Body脚手架**：提前列好步骤清单→每完成一步打勾→压缩后读回文件就知道到哪里了

### 原则三：方法论必须少而精

- **为什么**：Skill本身也占上下文→方法论越长，留给干活的空间越少
- **Grade Skill只有3句话**→占用极少上下文→省下的空间给模型发挥
- **设计原则**：用最少的话，把模型从默认路径推到正确路径

## 七、Skill矩阵（工具箱全览）

| 阶段 | Skill | 核心功能 | 金句/要点 |
|:--|:--|:--|:--|
| 需求对齐 | **Grade** | 榨干想法，沿设计树逐一讨论 | 目标：直到共识。Plan模式目标是赶紧出计划 |
| 方案验证 | **原型** | 快速生成可测试原型 | 用数据说话，不靠感觉选方案 |
| 需求沉淀 | **To PRD** | 把对话精华写成需求文档 | 下一个Agent永远无法访问本次对话 |
| 任务拆分 | **To Issue** | 垂直切片拆分，支持并行 | 每个切片独立可验证 |
| 编码 | **TDD** | 测试驱动开发 | 先红灯→绿灯→重构 |
| 质量 | **代码审查** | 核弹级严格审查 | 重点：结构简化、防打补丁、去AI垃圾 |
| 验证 | **E2E测试** | 端到端自动测试 | 只记录Bug事实，不写修复建议 |
| 验证 | **手工分组测试** | 最后防线 | 一条路径走完，不来回切 |
| 修复 | **Bug Fix** | 7阶段系统修复 | 防打补丁→找根因→沉淀经验 |
| 交接 | **Handoff** | 上下文超限时写交接文档 | 只写问题B，已解决的不要混入 |
| 工具 | **LSP** | 精准定位代码 | 把翻15个文件变成一步到位 |
| 演化 | **代码库质量** | 定期审查整体架构 | 让代码库越来越好维护 |

## 八、金句集锦

1. **不要让模型窗口超过30万**——超过之后它变得很蠢很蠢。
2. **AI不是你肚子里的蛔虫**——信息没对齐就开工 = 注定返工。
3. **没有一个好的方法论，它就永远走平庸的路径。**
4. **Plan模式的目标是赶紧出计划，Grade的目标是直到我们达成共识。**
5. **让E2E Agent写修复建议 = 邀请它给你的代码库打一堆补丁。**
6. **你给AI改Skill，它就用打补丁的方式改——最后变成补丁的补丁的补丁。**
7. **知识沉淀 = 把每次对话的成果从"一次性消耗品"变成"持续积累的复利"。**
8. **这套方法不仅适用于代码，适用于任何你需要让AI帮你干活的领域。**
9. **最小必要干预：非必要不干预，但关键路径上必须给到方法论。**

## 九、行动指南：如果你现在就想开始

### 24小时内可做

- 装一个上下文进度条插件，开始盯住窗口数字
- 新建一个"知识沉淀文档"，把当前项目的关键业务术语写进去（哪怕只写3条）

### 一周内可做

- 下一个需求用 Grade Skill 聊，对比之前用 Plan 模式的区别
- 聊完后用 To PRD 写成需求文档，体验"新会话只读PRD、零追问"的感觉

### 一个月内可做

- 建立起完整的9步闭环（哪怕最初几步手动完成）
- 跑通一次 Handoff 交接（上下文到15万→写交接→开新会话→继续）
- 跑通一次 Bug Fix → 知识沉淀的完整循环
